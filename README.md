# Связка: локальный MVP, этапы 1–4

К существующему интерфейсу подключены PostgreSQL, NestJS API, настоящая авторизация, Creator Kit с приватным MinIO, заявки, партнёрские связи, click tracking, CSV-заказы, атрибуция, комиссии, ledger и ручные выплаты.

Текущая версия: `0.4.0`. История изменений находится в `CHANGELOG.md`. Проект распространяется как proprietary software; условия указаны в `LICENSE`.

> **Важно для безопасности:** Файловый pipeline MVP не включает антивирусную проверку. Использовать только в закрытом пилоте с проверенными брендами. Перед публичным запуском подключить quarantine, ClamAV и worker

Исходный интерактивный прототип сохранён без изменений в папке `prototype/`. Контрольные суммы находятся в `prototype/SHA256SUMS`.

Рабочее приложение находится в папках `frontend/` и `backend/`. Для проверки MVP используйте адрес frontend после запуска Docker.

## Клонирование проекта

```bash
git clone <адрес-репозитория> svyazka
cd svyazka
cp .env.example .env
docker compose up --build
```

Замените `<адрес-репозитория>` на адрес, по которому проект будет опубликован. Placeholder-значения из `.env.example` подходят только для локального тестового запуска. Перед размещением в сети обязательно задайте собственные случайные секреты.

## Что потребуется

1. Компьютер с macOS, Windows 10/11 или современным Linux.
2. Docker Desktop.
3. Не менее 4 ГБ свободной оперативной памяти.
4. Свободные порты `5173`, `3000`, `5432`, `9000` и `9001`.

Node.js для обычного запуска через Docker не обязателен.

## Установка Docker Desktop

1. Откройте официальный сайт Docker и скачайте Docker Desktop для своей системы.
2. Установите программу обычным способом.
3. Запустите Docker Desktop.
4. Дождитесь сообщения, что Docker Engine работает.
5. На Windows при запросе установки WSL 2 согласитесь и перезагрузите компьютер.

Проверка установки в терминале:

```bash
docker --version
docker compose version
```

Обе команды должны показать номера версий.

## Настройка окружения

Откройте терминал в папке проекта и создайте локальный файл настроек:

```bash
cp .env.example .env
```

Для первого локального запуска значения по умолчанию работоспособны. Перед передачей проекта другим людям или размещением в сети замените:

```dotenv
POSTGRES_PASSWORD=придумайте_локальный_пароль
JWT_ACCESS_SECRET=случайная_строка_не_короче_32_символов
CLICK_IP_HASH_SALT=другая_случайная_строка_не_короче_32_символов
S3_SECRET_KEY=отдельный_случайный_локальный_секрет
```

Тот же пароль PostgreSQL должен быть указан внутри `DATABASE_URL` и `TEST_DATABASE_URL`.

Для локального HTTP должны оставаться:

```dotenv
COOKIE_SECURE=false
COOKIE_SAME_SITE=lax
FRONTEND_ORIGIN=http://localhost:5173
PUBLIC_BACKEND_URL=http://localhost:3000
```

В production используйте HTTPS и `COOKIE_SECURE=true`. Файл `.env` исключён из Git и не должен публиковаться.

## Первый запуск

Запустите весь проект одной командой:

```bash
docker compose up --build
```

Docker использует зафиксированный корневой `package-lock.json` и устанавливает зависимости через `npm ci`. Backend автоматически применит Prisma migrations. Первый запуск обычно занимает несколько минут. Терминал нужно оставить открытым.

После запуска:

- frontend: `http://localhost:5173`
- backend API: `http://localhost:3000/api`
- MinIO API: `http://localhost:9000`
- MinIO console: `http://localhost:9001`

MinIO console предназначена только для локальной диагностики. Логин берётся из `S3_ACCESS_KEY`, пароль — из `S3_SECRET_KEY`. Bucket `creator-kit` создаётся автоматически и остаётся приватным.

## Prisma migrations

Обычно миграции выполняются автоматически. Для ручного запуска в отдельном терминале:

```bash
docker compose exec backend npx prisma migrate deploy
```

## Тестовые данные

После первого запуска выполните seed:

```bash
docker compose exec backend npm run prisma:seed
```

Seed идемпотентный: его можно запускать повторно. Он создаёт:

| Роль | Email | Пароль по умолчанию |
|---|---|---|
| Бренд | `brand@example.test` | `BrandTest123!` |
| Креатор | `creator@example.test` | `CreatorTest123!` |
| Администратор | `admin@example.test` | `AdminTest123!` |

Пароли seed можно изменить в `.env` через `SEED_BRAND_PASSWORD`, `SEED_CREATOR_PASSWORD` и `SEED_ADMIN_PASSWORD`. Все аккаунты вымышленные; не вводите реальные персональные данные.

Seed также создаёт один опубликованный и один черновой оффер, Creator Kit, одобренную заявку, активную партнёрскую связь, тестовый Click, импорт, оплаченный заказ, доступную комиссию и `ACCRUAL` в ledger. Seed можно выполнять повторно без создания дублей. Файлы Creator Kit seed не загружает.

## Заявки и партнёрские связи

Креатор может подать одну ожидающую заявку на опубликованный оффер и отменить её до решения бренда. Бренд видит заявки только по собственным офферам и может одобрить или отклонить ожидающую заявку.

При одобрении одной транзакцией PostgreSQL заявка получает статус `APPROVED`, сохраняются дата и пользователь, принявший решение, а также создаётся `AffiliateRelationship` с уникальными `affiliateCode` и `promoCode`. `destinationUrl` копируется из проверенного `Offer.productUrl`.

Рабочая ссылка имеет вид:

```text
http://localhost:3000/go/{affiliateCode}
```

Маршрут работает только для связи `ACTIVE` и оффера `PUBLISHED`. Он создаёт `Click`, добавляет `click_id`, `affiliate_code`, `utm_source=svyazka`, `utm_medium=affiliate` и `utm_campaign`, затем перенаправляет на страницу товара. Если запись клика временно не удалась, redirect всё равно выполняется, а ошибка журналируется.

Сырой IP не сохраняется. Backend записывает только HMAC-SHA256 с серверной солью `CLICK_IP_HASH_SALT`. Короткое окно дедупликации и мягкий rate limit ограничивают очевидные автоматические повторы без скрытого fingerprinting.

Статусы связи:

- `ACTIVE`: ссылка работает, закрытый Digital Creator Kit доступен;
- `PAUSED`: ссылка не работает, связь можно активировать повторно;
- `REVOKED`: терминальный статус, ссылка и закрытый Digital-доступ отключены.

Для закрытых Digital-материалов используется `requiresAffiliateApproval`. Product Access по-прежнему не выдаётся.

## CSV, атрибуция и комиссии

Рабочий MVP-импорт выполняется в кабинете бренда в два шага: загрузка и предпросмотр, затем явное подтверждение. До подтверждения рабочие `Order` не создаются.

Обязательные столбцы CSV:

```text
external_order_id,order_date,amount_kopecks,currency,status
```

Необязательные: `returned_amount_kopecks`, `affiliate_code`, `promo_code`, `click_id`, `offer_id`. Поддерживается `RUB`, UTF-8, до 10 МБ и до 10 000 строк. Статусы: `pending`, `paid`, `cancelled`, `returned`, `partially_returned`.

Приоритет атрибуции: `click_id` → `affiliate_code` → `promo_code` → `UNATTRIBUTED`. Конфликтующие известные идентификаторы блокируют только соответствующую строку. Уникальность заказа обеспечивается по `brandId + externalOrderId`; повторная строка с разрешённым новым статусом обновляет заказ, а не создаёт дубль.

Ставки BPS копируются из оффера в заказ при первом импорте. Изменение оффера не меняет старые начисления. Расчёт выполняется через целочисленный `BigInt`:

```text
commissionKopecks = (amountKopecks × commissionBps + 5000) / 10000
```

Это округление до ближайшей копейки, половина вверх. Для частичного возврата комиссия пересчитывается от `amountKopecks - returnedAmountKopecks`, а разница записывается отрицательным `REVERSAL`. Ledger не удаляется и не переписывается.

`PAID` создаёт комиссию `HOLD`. Срок задаётся `COMMISSION_HOLD_DAYS`, по умолчанию 14 дней. Администратор вручную переводит истёкшие комиссии в `AVAILABLE`, создаёт payout, подтверждает его и отмечает выплаченным. Реальные платёжные сервисы не подключены.

Если возврат произошёл после выплаты, payout и выплаченная комиссия задним числом не меняются. Создаётся отрицательный `REVERSAL`, а задолженность сохраняется в `debtAmountKopecks` и отдельно показывается администратору.

## Аналитика по креаторам

`GET /api/brand/analytics/creators` строит отчёт по `Order.orderDate`, а не по дате импорта. Поддерживаются фильтры периода, оффера, креатора, статуса заказа и источника атрибуции, сортировка и пагинация. Ответ содержит строки креаторов и итог `total`.

Валовые продажи включают `PAID`, `PARTIALLY_RETURNED` и `RETURNED` до вычета возвратов. Чистые продажи включают `PAID` и остаток `PARTIALLY_RETURNED`; `CANCELLED` и полностью `RETURNED` исключаются. При отсутствии кликов `conversionRate` возвращается как `null`.

## Creator Kit и файлы

В закрытом пилоте поддерживаются:

- сохранение сценариев, фактов, формулировок, правил и требований в PostgreSQL;
- уровни `DIGITAL` и `PRODUCT`;
- загрузка одного файла через presigned URL;
- серверная проверка объекта через S3 HEAD после загрузки;
- одиночный просмотр и скачивание через временный presigned URL;
- отключение и повторное включение материала;
- фильтрация по уровню доступа, статусу, сроку действия и политике оффера;
- базовый расчёт заполненности Creator Kit.

Допустимые файлы:

| Категория | MIME и расширения | Максимальный размер |
|---|---|---:|
| Изображения | JPEG (`.jpg`, `.jpeg`), PNG (`.png`), WebP (`.webp`) | 25 МБ |
| Видео | MP4 (`.mp4`), WebM (`.webm`), QuickTime (`.mov`) | 500 МБ |
| Документы | PDF (`.pdf`) | 25 МБ |

На один оффер можно добавить не более 100 материалов. SVG, архивы и другие типы файлов отклоняются. Object key формирует только backend; frontend его не получает.

После прямой загрузки backend выполняет S3 HEAD и проверяет наличие объекта, точный размер, MIME и лимит размера. Эта проверка не анализирует фактическое содержимое файла и не заменяет антивирус.

Product Access хранится в структуре и доступен бренду в режиме предпросмотра. Реальным креаторам на этапе 2 выдаются только разрешённые Digital-материалы опубликованных офферов.

Не реализованы: антивирус, quarantine, worker, обработка медиа, preview-файлы, ZIP и пакетное скачивание, события скачиваний и расширенная статистика.


## Остановка и повторный запуск

Остановить проект, сохранив базу:

```bash
docker compose down
```

Повторно запустить с сохранёнными аккаунтами и офферами:

```bash
docker compose up
```

Данные PostgreSQL находятся в Docker volume `postgres_data`, файлы MinIO — в `minio_data`. Оба volume сохраняются при обычной остановке.

## Полная очистка тестовой базы

Команда удалит локальные контейнеры, базу PostgreSQL и все файлы MinIO. Все созданные аккаунты, офферы, Creator Kit и загруженные материалы будут потеряны:

```bash
docker compose down -v
```

Затем выполните первый запуск и seed заново.

## Типичные ошибки

### `docker: command not found`

Docker Desktop не установлен или ещё не запущен. Установите и откройте Docker Desktop, затем перезапустите терминал.

### `Cannot connect to the Docker daemon`

Docker Desktop установлен, но Docker Engine ещё запускается. Подождите 30–60 секунд и повторите команду.

### `port is already allocated`

Порт `5173`, `3000`, `5432`, `9000` или `9001` занят другой программой. Остановите другой локальный сервер или измените внешний порт в `docker-compose.yml`.

### Backend сообщает об ошибке подключения к PostgreSQL

Проверьте, что `POSTGRES_PASSWORD` совпадает с паролем внутри `DATABASE_URL` и `TEST_DATABASE_URL`. После изменения пароля в уже созданной базе выполните полную очистку через `docker compose down -v`.

### Не удаётся войти после seed

Повторите:

```bash
docker compose exec backend npm run prisma:seed
```

Убедитесь, что используете пароль из текущего `.env`, а не старое значение.

### Сессия не восстанавливается локально

Проверьте, что `COOKIE_SECURE=false`, frontend открыт именно по адресу `http://localhost:5173`, а `FRONTEND_ORIGIN` совпадает с этим адресом.

### Изменения frontend не появились

Обновите страницу без кэша. Если это не помогло:

```bash
docker compose down
docker compose up --build
```

### MinIO не запускается или файл не загружается

Проверьте состояние сервисов:

```bash
docker compose ps -a
docker compose logs minio minio-init
```

Убедитесь, что `S3_ACCESS_KEY` и `S3_SECRET_KEY` одинаковы для MinIO и backend, а `S3_ENDPOINT_PUBLIC=http://localhost:9000`. Для загрузки из браузера `FRONTEND_ORIGIN` должен совпадать с фактическим адресом frontend.

## Границы текущего MVP

На сервере работают:

- регистрация BRAND/CREATOR и вход;
- Argon2id-хеширование паролей;
- access JWT и ротация refresh-сессий;
- HttpOnly cookie с настройками для local/production;
- серверные роли, guards и проверка владельца;
- профили бренда и креатора;
- создание, редактирование и хранение собственных офферов;
- контролируемые переходы `DRAFT`, `PUBLISHED`, `PAUSED`, `ARCHIVED`;
- каталог опубликованных офферов для креатора.
- Creator Kit в PostgreSQL;
- приватный MinIO bucket;
- presigned upload/download;
- проверка владельца оффера и серверная фильтрация материалов;
- одиночная загрузка, скачивание, отключение и включение файлов.
- заявки креаторов на опубликованные офферы;
- одобрение, отклонение и отмена заявок;
- уникальные партнёрские ссылки и промокоды;
- пауза, активация и отзыв партнёрской связи;
- защищённый redirect `/go/:affiliateCode`;
- закрытые Digital-материалы для активных партнёров.
- Click tracking без хранения сырого IP;
- двухшаговый импорт заказов через CSV;
- атрибуция по click, affiliate и promo codes;
- заказы, возвраты и снимки ставок BPS;
- комиссии `PENDING`, `HOLD`, `AVAILABLE`, `PAID`, `REVERSED`;
- неизменяемые `ACCRUAL`, `REVERSAL` и `PAYOUT` ledger entries;
- ручные выплаты администратора;
- продажи и доход в кабинетах бренда и креатора;
- отчёт бренда по креаторам и итоговая строка.

Не подключены к серверу:

- образцы и Product Access;
- AI-генерация;
- JavaScript tracker, CMS и server-to-server интеграции;
- реальные платёжные сервисы и автоматические выплаты;
- прочие демонстрационные функции административной панели.
- production media pipeline, антивирус, quarantine, worker, preview и пакетное скачивание.

Денежные значения хранятся целыми числами в копейках. Комиссии хранятся в базисных пунктах с диапазоном `0..10000`. Размер файлов хранится как Prisma `BigInt`; backend явно сериализует такие значения в JSON-строки.
